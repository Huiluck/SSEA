### 3.3 实验 3：0/33 是真的，成因有两条，已复核

与实验 2 相反，这一条**不是判据问题**：

- 33 次调用**全部** `SKILL_FAILURE`，且**两条独立成因**已逐层实读代码复核：
  1. `precondition["min_energy"] = 0.99` 取自**抓取之后**的近满能量，而能量此后只降不升
     → 每次重放都卡在 `precondition_failed`（41 次中止中 37 次）。
  2. 重放的**第一帧**就是那个**已被消费的** `grasp`（窗口建立时资源已被抓走）
     → 对已不存在的目标执行抓取。
- 更刺眼的一格：**编译出技能的那一段成功段长达 41 帧，而调用它时每一次都报失败**。
  「编译它的那一段成功」与「重放它时成功」**不是同一件事**。

> **两把尺的问题**：编译判据是**回溯性**的（窗口净收益 > 0），
> 重放判据是**前瞻性**的（逐帧硬判 + 前置条件快照）。
> 同一份 trace 被两把不同的尺量，结论当然可以相反。
> 这是当前最值得查的一处——**在归因到「技能表示丢了信息」之前，先确认两把尺是不是在量同一件事。**

### 3.4 读数字的三条纪律

1. **测试全绿只说明工程质量。** 它证明的是协议自洽、序列化保真、约束不被违反、
   注入面四条性质成立。它**不**证明这个架构更省算力、记忆提升了生存率、
   技能固化降低了消耗。项目咬过的坑（`get_threshold()` 无消费者、
   `UPDATE_RETRIEVAL_POLICY` 写出下游读不懂的形状、记忆门半开、
   事件环形缓冲静默漏、`max_events=0` 静默无界）**全部发生在测试全绿的状态下**。
2. **一个饱和的率不能作证据。** `危险回避率` 两臂都是 **0.9814**——
   分母只有 336 个暴露帧、分子只有 6 次接触，**一次接触就够让一个 seed 的率跳几个百分点**。
   它算对了，但量不出东西。**这比把 `None` 写成 `1.0` 更难发现：数字本身完全正常。**
3. **量不出差的时候，先怀疑尺子。** 判据的分辨率低于效应幅度时，
   「**没有差别**」与「**量不出差别**」的输出**完全一样**。
   所以判读顺序是**从细到粗**：细档说「一样」才是真的没动；
   粗档说「一样」而细档说「不一样」时，**以细档为准**。

> 是**变异测试找出来的，不是读代码读出来的**；`serialization` 那条是**撞出来的**
> （给快照包 `MappingProxyType` 之后它立刻抛 `TypeError`）；
> `FastLoop` 判空是**一个失效的探针工具反向撞出来的**。
> **读一遍代码不会发现它们，改一处别的东西才会。**

## 6. 复现

```bash
# 全套测试（910 passed, 1 skipped）
.venv/Scripts/python.exe -m pytest tests/ -q

# 顺序不变性 —— 每次改动后都必须复跑，不只默认顺序
for i in $(seq 0 14); do
  .venv/Scripts/python.exe -m pytest tests/ -q --randomly-seed=$i
done

# 七个验收实验：一次跑完已就绪的五个（未落地的两个不会假装跑过）
.venv/Scripts/python.exe -m experiments.run_all 200
.venv/Scripts/python.exe -m experiments.exp2_memory_recall 200   # 单跑，看三档判据
```

> **复跑时不要一边改文件。** 本次收尾时又踩了一次：后台的 15-seed 循环在跑，
> 同时准备编辑工作树。**一个后台跑的验证循环，前提是工作树在这段时间里不动**——
> 否则循环里可能有一轮正好在文件写了一半时收集到它，
> 症状看起来**完全像「随机顺序暴露了一个真缺陷」**（13 §7 有完整记录）。

**中文输出需要 `PYTHONIOENCODING=utf-8`**，否则 Windows 控制台会因编码报错。
