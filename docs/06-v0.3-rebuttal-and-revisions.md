# 一、问题 1：任务是设计新模型架构，但现在看起来只是使用已有架构作为大脑

## 1. 这个问题成立

任务书 v0.3 中确实有一个表达风险：

> 过度强调使用 GRU、Mamba、LoRA、RAG、Voyager 等已有成果，导致看起来像是在做“现有架构的应用集成”，而不是“设计新的模型架构”。

如果项目目标只是：

```text
拿一个现有模型
+
放进环境
+
让它自我迭代
```

那么它确实不够构成“新的模型架构”。

所以这里必须澄清：

> 第一阶段可以使用已有算子作为可替换组件，但项目真正的架构创新不在算子本身，而在模型整体的组织结构、控制方式、学习方式和演化方式。

---

## 2. “模型架构”可以分为四个层次

我们需要区分四个层次：

| 层次 | 含义 | 例子 |
|---|---|---|
| L1 算子层 | 基础网络模块 | GRU、Mamba、Attention、MoE、SSM |
| L2 信息流层 | 模型内部各模块如何连接 | 感知 → 状态 → 记忆 → 动作 |
| L3 学习层 | 模型如何更新自身 | 权重更新、记忆写入、技能固化、代码修改 |
| L4 演化层 | 模型如何保存、继承、变异 | 基因包、本能继承、变异、自我修改 |

传统 LLM 的架构主要是：

```text
文本输入
→ embedding
→ Transformer blocks
→ language head
→ token 输出
```

它的核心是：

```text
语言建模架构
```

而 SSEA 要设计的是：

```text
生存控制架构
```

因此，SSEA 的新架构贡献应该定义在 L2、L3、L4，而不是只发明一个新的 L1 算子。

---

## 3. SSEA 的真正架构创新点

建议明确写入任务书：

### 创新点一：从“语言生成架构”转向“生存控制架构”

传统模型的核心任务是：

```text
预测下一个 token
```

SSEA 的核心任务是：

```text
感知 → 决策 → 行动 → 反馈 → 学习 → 遗传
```

这不是简单替换 backbone，而是改变模型的主任务。

---

### 创新点二：权重、记忆、技能三分离

传统模型把大量知识压在权重里：

```text
知识 ≈ 权重
```

SSEA 将模型能力分为三类：

```text
基础控制能力 → 小型核心权重
历史事实经验 → 外部记忆系统
可执行行为 → 技能库 / 代码库
```

这是一种架构层面的改变。

它直接影响：

- 算力消耗
- 带宽消耗
- 精准回忆
- 自我修改
- 遗传传递

---

### 创新点三：动作不是语言输出，而是多通道控制信号

SSEA 的模型输出不是：

```text
“我决定向左走并尝试获取资源。”
```

而是：

```text
运动向量
操作参数
技能调用
记忆写入
通信向量
自我修改提案
```

这改变了模型的输出空间。

---

### 创新点四：学习不只依赖全量权重训练

SSEA 的学习机制包括：

```text
记忆写入
技能固化
规则生成
局部参数更新
小型 adapter 更新
代码修改
```

这与传统“喂数据 + 反向传播 + 全量更新”不同。

---

### 创新点五：模型具有可遗传结构

SSEA 的模型不只是被训练，还可以被：

```text
保存
恢复
复制
变异
继承
```

它的可遗传对象包括：

```text
架构
核心权重
本能 adapter
技能库
记忆索引
行为策略
代谢策略
```

这是一种生命周期架构。

# 二、问题 2：如何做到模型与生态系统之间的交互不是自然语言，而是身体行为等？

## 1. 这个问题成立，而且必须通过接口强制实现

如果只是口头说“不用自然语言”，但系统仍然允许模型输出字符串，那么最后很可能还是回到语言模型。

所以必须做强制设计：

> 环境只接受结构化动作对象，不接受自然语言字符串。  
> 模型控制闭环中没有 tokenizer，没有 language head，没有文本生成接口。

---

## 2. 非自然语言交互的实现原则

### 原则一：环境不接收自然语言

环境接口应定义为：

```python
def step(action: Action) -> tuple[Observation, Feedback]:
    ...
```

而不是：

```python
def step(text_command: str):
    ...
```

也就是说：

```text
环境不接受 str 类型命令。
```

如果模型输出自然语言，环境无法执行。

---

### 原则二：观测不主要返回自然语言

环境返回的是：

```python
Observation = {
    body: BodyState,
    objects: list[ObjectVector],
    events: list[EventVector],
    environment: EnvironmentSummary
}
```

而不是：

```text
“你看见左边有一只野兽。”
```

观测应是：

```text
对象向量
事件向量
身体状态
环境摘要
```

---

### 原则三：模型控制路径不经过语言头

模型内部即使存在语言模块，也不允许直接进入控制闭环。

控制闭环必须是：

```text
Observation
→ Perception Encoder
→ State Core
→ Action Head
→ Action
→ Environment
```

而不是：

```text
Observation
→ LLM
→ text
→ parse text
→ action
```

后者可以作为慢速规划层，但不能作为主控制环。

---

## 3. 模型如何以身体行为交互？

模型通过三类信号与身体和环境交互。

---

### 第一类：感知信号

模型“看”到的不是文字，而是结构化感知：

```python
ObjectVector = {
    "object_id": "obj_17",
    "category_id": 3,
    "distance": 4.2,
    "direction": [0.8, 0.6],
    "resource_value": 0.7,
    "threat_level": 0.1
}
```

这表示：

```text
一个资源对象在右前方，距离 4.2，资源价值 0.7，威胁 0.1。
```

而不是：

```text
“前方有一个资源。”
```

---

### 第二类：动作信号

模型输出不是文字，而是控制参数：

```python
Action = {
    "locomotion": {
        "direction": [0.8, 0.6],
        "speed": 0.5
    },
    "manipulation": {
        "target_id": "obj_17",
        "operation": "grasp",
        "force": 0.4
    }
}
```

这表示：

```text
向右前方移动，速度 0.5，并尝试以 0.4 力度抓取 obj_17。
```

---

### 第三类：记忆与技能信号

模型不是用语言描述经验，而是写入向量与结构化记录：

```python
MemoryItem = {
    "type": "EVENT",
    "context_vector": [...],
    "content_vector": [...],
    "outcome": "energy_gained",
    "importance": 0.8
}
```

---

## 4. 自然语言放在哪里？

自然语言可以作为后续观察员接口：

```text
人类观察员询问：你为什么这样做？
模型事后生成解释。
```

但自然语言不能参与底层控制：

```text
自然语言不是感知输入。
自然语言不是动作输出。
自然语言不是主训练信号。
```

这样可以保证模型与生态系统的交互是：

```text
身体状态
环境对象
动作信号
能量变化
损伤变化
事件记忆
```

而不是：

```text
文本输入 → 文本输出
```

# 三、问题 3：`available_actions: list[str]` 是否意味着动作只是从有限集合中选择？如果大脑基于现有架构，如何指挥身体？

## 1. 原任务书中的接口确实需要修订

你指出的问题很准确。

原接口：

```python
BodyState = {
    ...
    "available_actions": list[str],
    ...
}
```

这个写法容易被理解为：

```text
模型只能从有限字符串列表中选择动作。
```

这会带来两个问题：

1. 动作空间过于离散。
2. 看起来像菜单选择，而不是连续身体控制。
3. 不利于模型产生新动作或新技能。
4. 不符合“高密度动作信号”的目标。

因此必须修订。

## 2. `available_actions` 不应是动作空间，而应是动作约束

应将其改为：

```python

```

它只表示当前身体能做什么、不能做什么，而不是动作本身。

例如：

```python
ActionConstraints = {
    "max_speed": 1.0,
    "max_force": 0.8,
    "allowed_operations": ["grasp", "push", "pull"],
    "forbidden_targets": ["obj_99"],
    "energy_budget": 12.5,
    "can_communicate": True,
    "can_self_modify": False
}
```

它的作用是约束动作，而不是定义动作。

---

## 3. 动作空间应重新定义

动作不应只是：

```text
从 list[str] 中选择一个字符串
```

而应定义为混合动作空间：

```text
连续动作
+
离散动作
+
参数化动作
+
技能调用
+
潜空间动作
```

# 五、现有架构如何指挥身体？

你提到“如果模型基于现有架构做大脑，那么该架构输出自然语言。怎样令这个架构指挥身体做动作？”

这里需要区分两种情况。

---

## 情况一：使用 GRU / Mamba / 小型状态核心

这类架构本身并不天然输出自然语言。

它们输出的是：

```text
hidden_state
```

例如：

```python
h_t = GRU(x_t, h_{t-1})
```

然后我们可以接一个动作头：

```python
a_t = ActionHead(h_t)
```

而不是接语言头：

```python
token_logits = LMHead(h_t)
```

所以，如果使用 GRU/Mamba，控制路径是：

```text
Observation
→ Perception Encoder
→ x_t
→ GRU/Mamba
→ h_t
→ Action Head
→ Action
```

不经过自然语言。

---

## 情况二：使用预训练语言模型或 Transformer Decoder

如果选择的基础架构本来会输出自然语言，那么必须增加一个“动作翻译/控制层”。

但这里要非常谨慎。

### 不推荐的主路径

```text
LLM 输出自然语言
→ 解析自然语言
→ 转换为动作
```

例如：

```text
模型输出：“向左移动并抓取资源。”
解析器将其转换为动作。
```

这种方式可行，但不理想：

- 带宽低
- 延迟高
- 容易歧义
- 不利于低算力
- 仍然依赖语言中心范式

它只能作为慢速规划层，不能作为主控制环。

---

### 更推荐的改造方式

如果使用 Transformer/LLM 类架构，应移除或冻结语言头，替换为动作头：

```text
hidden_state
→ Action Head
→ continuous action
→ parametric action
→ skill selection
→ memory operation
```

即：

```python
a_t = ActionHead(transformer_hidden_state)
```

而不是：

```python
text = tokenizer.decode(lm_head(hidden_state))
```

---

## 情况三：保留语言能力，但只作为慢环解释器

如果未来需要模型与人类交流，可以设计双环架构：

```text
Fast Loop：快速身体控制环
Slow Loop：慢速语言/规划环
```

### 快环

```text
感知 → 状态核心 → 动作头 → 身体
```

要求：

- 低延迟
- 低带宽
- 非语言
- 连续控制

### 慢环

```text
记忆 → 规划 → 语言解释 → 人类观察员
```

要求：

- 可解释
- 可审计
- 不直接控制身体
- 只产生建议或计划

慢环输出如果要影响身体，必须经过：

```text
Action Compiler / Validator
```

也就是：

```text
语言计划
→ 结构化动作
→ 安全检查
→ 身体执行
```


它不是语言模型头。

# 八、对“动作是否从有限中选择”的正式回答

修订后的回答是：

```text
不是。
```

动作空间包括：

```text
连续控制空间
参数化动作空间
技能调用空间
潜空间动作
```

`allowed_operations` 和 `action_constraints` 只是约束，不是动作本身。

例如模型不是选择：

```text
"go_left"
```

而是生成：

```python
{
    "direction": [-0.7, 0.2],
    "speed": 0.43,
    "duration": 1.2
}
```

也可以生成新技能：

```python
{
    "skill_id": "approach_resource_from_cover",
    "params": {
        "target_id": "obj_17",
        "approach_angle": 0.8,
        "stop_distance": 0.5
    }
}
```

技能库可以增长，因此动作空间不是封闭有限集合。

# 九、最终答辩结论

---

## 对问题 1 的结论

原任务书确实需要更明确地说明：

> SSEA 不是简单使用已有架构作为大脑。  
> 第一阶段使用已有算子只是为了验证新架构的信息流。  
> 真正的新架构体现在：生存控制闭环、权重/记忆/技能分离、非语言动作接口、局部学习、遗传与自我修改。

---

## 对问题 2 的结论

非自然语言交互必须通过强制接口实现：

```text
环境不接受自然语言输入。
模型控制闭环不使用 tokenizer。
模型输出不是文本，而是结构化动作。
自然语言只能作为后续观察员解释接口。
```

---

## 对问题 3 的结论

原接口中的：

```python
available_actions: list[str]
```

容易造成误解，应修订为：

```python
action_constraints: ActionConstraints
```

动作本身应为：

```text
连续动作
+
参数化动作
+
技能调用
+
潜空间动作
```

如果大脑使用 GRU / Mamba，则不接语言头，而接动作头。

如果使用已有语言模型，则必须将其语言输出限制在慢环解释层，不能直接控制身体。
