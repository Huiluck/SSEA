## 1. 一句话定位

- **论文主张**：用 18 个约 200 LOC 的「小编译器」把 Python 的 HumanEval/MBPP（函数签名、单元测试、doctest、术语、类型标注）批量转译到 18 门语言，得到首个大规模并行多语言代码生成基准，并据此评测 Codex / CodeGen / InCoder（§1、§3.3、Table 1）。
- **对 SSEA 的意义**：**无**——本篇输入是自然语言 docstring、输出是代码、判据是聚合 pass@k 分数，三者分别违反 C2、C1、C9；无法回溯到 C1–C10 任何正向约束，仅可作**反面参照 + 判据口径对照**保留在论文池（§6）。

## 2. 问题 — 机制 — 证据

### 2.1 论文要解决的问题
- 代码生成模型大多只在 Python 上评测，多语言能力未知；需要**并行（parallel）**、可扩展的评测基准（§1）。既有缺陷：文本相似度指标（BLEU/CodeBLEU）与正确性弱相关，须用隐藏单元测试（§2.3）；Xu et al. 只用 perplexity 且仅对 Python 验正确性；MBXP 把测试用例直接喂给模型、类型转译不忠实（§8）。

### 2.2 核心思想（关键 insight）
1. **转译而非重写**：基准只需转译四个成分——函数签名、简单单元测试、描述注释、类型标注；**函数体不转译**（那正是模型要生成的），故每编译器约 200 LOC（§1、§3.3）。
2. **隐藏测试 + 二值判定**：抽走 MBPP 原本随 prompt 给出的断言改为隐藏测试，签名由断言反推补上，使模型看不到被测用例（§3.1、Fig. 3；§8 对 MBXP 的对比）。

### 2.3 关键机制 / 算法（可独立搬运的「零件」清单）
| 零件 | 输入 → 输出 | 作用 | 出处 |
|---|---|---|---|
| 基准转译编译器 ×18 | Python 题 → 目标语言 prompt | 一份基准低成本复制到 N 门语言 | §1、§3.3、Table 1（LOC 38–479） |
| 值-值递归编译器 + 类型转译/推断 + 术语改写 | Python 一等值/可选标注/术语 → 目标值/静态类型（`Optional[X]`→ADT）/目标术语 | 支持 C++/Rust/Swift/Scala 等强类型目标，消除 prompt 语言错配 | §3.3.1–3.3.4、Fig. 4–5 |
| 容器化沙盒 + 错误分类法 | 生成代码 → 编译/超时/跑隐藏测试/归因 | 统一判定与失败归因（RUNTIME/STATIC/TYPE/LANGUAGE/MODEL） | §1、§6.5、Table 25–28 |

### 2.4 关键表示与数据结构
- prompt 三段式：签名 + 自然语言注释 + doctest；**不给显式目标语言提示**，语言线索全在语法/术语中（§2.1、Fig. 1a）。判据为 pass@k（T=0.2 取 pass@1，T=0.8 取 pass@10/100；每题 200 采样，无偏估计量，§4.2）；语言频度分档 NICHE/LOW/MEDIUM/HIGH（§3.2、Table 1）。

### 2.5 实验证据
| 任务 / 基准 | 对照基线 | 关键数字 | 统计口径 |
|---|---|---|---|
| Codex · MultiPL-HumanEval | 原文 Python HumanEval | Python pass@1 45.9%（原论文 28.8%） | T=0.2，200 采样，§5.1.1 |
| Codex · JavaScript | 同模型 Python | 高于 Python +2.3%，**不显著**（p=0.43） | 混合效应模型，§5.1.2 |
| perplexity vs 正确率 | Xu et al. 的 perplexity | 无强相关（JS/TS perplexity 最高、pass@1 也最高） | Fig. 8、§5.1.4 |
| 语言频度效应 | HIGH 组 | MEDIUM/LOW/NICHE 差异 p=0.006/<0.001/0.002，但 Lua 仍排第 9 | §5.1.3 |
| 类型标注消融 | 有/无标注 | HE p=0.33；MBPP p=0.23；TS 全改 `Any` −2.5%（p<0.001）；Python 去标注 p=0.23 | §6.2–6.2.3 |
| 转译成分消融 | Test-only 转译 | Full vs Test-only p=0.03；No-Doctests vs Test-only p<0.001；No-Translation vs Test-only p=0.2 | Codex，§6.1 |

### 2.6 论文自陈局限与边界条件
- **代表性威胁**（§7）：同一批「基础编程题/面试题」投给脚本语言与系统语言，实际用途迥异，基准分未必代表真实水平。
- **prompt 敏感**（§7）：注释风格、参数命名等小改动即显著改变 pass rate（§6.3），各语言分数可被进一步调优抬高。**采样配置**沿用 Python 最优设置，未必适合其他语言。
- **转译覆盖**（§3.4）：164 题中排除 3 题、改写 2 题、强类型语言最多 5 题类型不可转译而失败；C 与 SQL 因无自然对应类型被排除；不支持高阶函数的测试。论文**未提及**任何控制环、生存任务、记忆、自修改、演化/继承机制。

## 3. SSEA 立场对齐（核心维度）

### 3.1 C1–C10 映射
| 裁判标准 | 判定 | 依据（论文中的具体机制/数字） | 若冲突：改造方向 |
|---|---|---|---|
| **C1** 生存控制架构，非语言生成 | **✗** | 全篇目标是 NL2Code：自然语言描述 → 函数体（§2.1、Fig. 1），无控制环、无生存变量、无淘汰信号 | 无法改造：不同问题类 |
| **C2** 自然语言只作观察员接口 | **✗** | docstring 是 prompt 的必要组成，且 doctest 的有无直接改变 pass@1（No-Doctests vs Test-only p<0.001，§6.1）——语言在性能闭环内 | 无法改造：与「会说≠会做」相反 |
| **C3** 权重/记忆/技能三分离 | **✗** | 仅评测单一 LLM 的采样输出（§4.1），无权重/记忆/技能分置 | 不适用 |
| **C4** 低算力、低带宽 | **✗** | 每题每温度 200 采样（§4.2），单语言约 32,000 个 Codex 完成（附录 D），19 语言 × 3 模型 | 反向参考：SSEA 慢环预算须显式定义，不可沿用大采样口径 |
| **C5** 精准回忆历史 | **—** | 无记忆机制；「历史」仅指不可检索、不可写入的训练语料（§4.1） | 不适用 |
| **C6** 可自主修改自身 | **—** | 未提及；被评模型为冻结权重 | 不适用 |
| **C7** 可保存/恢复/变异/继承 | **—** | 未提及；无 GenePackage 类结构 | 不适用 |
| **C8** 给基因先验，不给知识语料 | **✗** | 能力全部来自代码语料预训练（InCoder 159GB 代码 + 57GB StackOverflow；CodeGen 先 Pile 825GB 再 BigQuery 6 语言子集，§4.1） | 不适用 |
| **C9** 不设外部评分函数，只有淘汰函数 | **◐** | 单题判定是**二值隐藏单元测试**（通过全部测试才算对，§2.3、§3.3.1），与「验证门只判合法性、不打分」同形；但主指标 pass@k 是对模型的**外部聚合打分与排序**（§4.2、Fig. 6–9），属违规 | 只取前半：二值隐藏测试可作环境侧合法性门，须剥掉 pass@k 聚合排名 |
| **C10** 创新在 L2/L3/L4，不在 L1 算子 | **—** | 不涉及架构分层；Transformer 仅作被评对象（§4.1） | 不适用 |

> 小结：10 条中 6 条 `✗`/`—` 为硬不适用；唯一有张力的是 C9 的**半条**（二值隐藏测试 vs pass@k 聚合打分）。

### 3.2 L1–L4 定位与模块映射
— 论文不提供任何 L1–L4 构件，也无构件可映射到 SSEA 现有模块；被评模型只是 L1 算子的现成消费者，本篇本身不在四层内。

### 3.4 债务与验收实验对应
- 可回应的已知债务：**仅间接**——「隐藏测试 + 二值通过/失败」口径可作债务 25/26/27/28（判据形状错、环境对无消费者通道报成功、技能失效被判成成功）的**外部对照形状**：正确性须由被测行为的实际结果判定，而非由机制是否存在判定。可服务的验收实验：无（技能固化实验 3 的 0/33、记忆检索命中率均不在本篇射程内）。

## 5. 冲突、代价与风险
- **与硬约束的冲突**（对应 3.1 中 ✗/◐）：C1/C2 语言是能力载体而非观察员接口，不可调和，不做改造尝试；C8 能力全部来自知识语料，与「基因只放结构性先验」相反；C9 的 pass@k 是外部聚合评分与排序，若误搬会把 SSEA 验证门变成打分排行榜；C4 采样规模（200 × 多温度 × 19 语言）与低算力冲突，且论文自陈 perplexity 不可作代理（§5.1.4）。
- **隐含假设与失效条件**：假设「Python 一等值有目标语言自然对应物」（§3.4），故 C 与 SQL 被排除；假设「同一批基础题对所有语言等难度」，论文自己在 §7 承认不成立。
- **工程代价与退化模式**：对本项目为零（不引入运行组件，仅作文献参照）；但若把 pass@k 式聚合分数引入 SSEA 验收，典型退化是**「分母掩盖机制失败」**——聚合分尚可而底层机制从未触发（正对应实验 3 的 0/33 未被聚合分数暴露）。

## 6. 组合分析

- **关系图谱**：无可点名的前置依赖/互补/替代对象。它不与第 3 节任何卡片（Memento、FLEX、PSN、MemRL、A-MEM、LightMem、SEDM、SkillWeaver、Voyager 等）共享机制，也无法与之组合——那些卡片都在处理「记忆/技能/参数如何组织与更新」，本篇只在处理「如何用语言模型的采样结果算分」。**组合价值 = 0**。
- **本篇在组合中的典型角色**：**判据形状的对照臂（反例）**——用「pass@k 聚合分」与「机制计数（技能是否真被调用/固化）」两种判据对比，验证 SSEA 验收是否会被聚合分数掩盖机制性失败（服务债务 25–28）。

## 8. 裁决与下一步

- **应用等级**：**E 不采用** —— 理由：本篇是 LLM 代码生成的评测基准，其机制（语言 prompt → 代码 → pass@k）与 C1/C2/C3/C8 全线不兼容，C9 上其主指标恰是「外部评分函数」的典型反例；无任何可接入构件。仅保留「隐藏测试二值判据」口径作对照。
- **优先级**：P3
- **建议动作**：① 归档到 `cards/README.md` 的「立场无关 / 反面参照」分组，标注触发条件「仅在讨论验收判据形状时复查」；② 不建 issue、不排期。
- **最小验证实验**（若日后确需复检判据形状）：在技能固化实验 3（当前 0/33）上设双臂——A 臂用**聚合通过率**判据（pass@k 式），B 臂用**机制计数**判据（技能是否被调用 + 行为是否改变）；判据先看分母（分母 = 33 个固化机会），A 臂报通过率、B 臂报「被调用次数/行为改变次数」；预期 A 臂给出非零分数而 B 臂仍 0/33（聚合分数掩盖机制未触发），若两臂结论一致则担忧被证伪。
- **若 E 不采用**：原因 —— ① 问题类不同（语言生成 vs 生存控制）；② 主指标违反 C9；③ 能力来源违反 C8；④ 无 L2/L3/L4 构件。保留在论文池的理由：作为 C1/C2/C9 的清晰反面参照，并在讨论验收判据形状（债务 25–28）时提供已发表的对照口径。
